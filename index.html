Abstract

TL;DR We treat a recaptioned corpus as a supervision distribution set by its captioning policy, captioner and source corpus, and audit it inside one 64-lexical-unit window with a five-axis profile whose shared unit is the controllable basic unit (CBU), re-asked against the paired image by two judges from different model families and checked against human ratings on sampled claims.

Recaptioned image-text corpora are now standard for text-to-image (T2I) training, with VLM captioners replacing sparse alt-text by dense descriptions. Yet a recaptioned corpus is not only a collection of captions: it is a supervision distribution induced by a documented captioning policy (π), captioner (Vc), and source corpus (C). Length-correlated proxies miss caption-register artifacts and downstream T2I benchmarks entangle the corpus with training choices, so this distribution is hard to audit at corpus scale. We introduce a reusable matched-budget audit framework for recaptioned supervision distributions Dπ,Vc,C: at a fixed B = 64 lexical-unit window it reports a five-axis profile spanning prompt-side coverage, image-conditioned faithfulness, and caption-surface health, with claimed controllable basic units (CBU) as the shared denominator. We instantiate the framework on seven paired comparisons over five public source corpora. Across the four cross-corpus pairs, the released surface raises supported CBU per caption by to under both Qwen and Gemma Judges, and on CC12M the same framework exposes a long-vs-dense frontier that is consistent across both judges and four budgets. We release the audited multi-source recap corpus together with the audit-artifact bundle.

What the audit measures

The framework is a reusable audit operator over recaptioned supervision distributions. Its target is a documented operating point Dπ,Vc,C: the joint over caption c and source image x induced by captioner Vc under policy π on source corpus C. Each caption set over the same source rows is a surface.

The audit asks what supervision signal a text-to-image model would consume, without training or ranking a particular generator. It runs four passes over source-aligned rows and returns a five-axis profile; each axis states the boundary of what it certifies.

Controllable basic units

A CBU is a caption claim of one of eight semantic visual-claim types: object, attribute, relation, count, style, camera, lighting and text-rendering. The extractor finds CBUs caption-only and the judge re-asks each one against the paired image, so claimed density, supported yield and unsupported risk share one denominator. With c≤B the B-word window of caption c and ℓ(·) its length in lexical units:

Claimed density CBU/cap(Dc, B) = 𝔼c∼Dc[ |φ(c≤B)| ] (1)
Lexical efficiency CBU/100 lex(Dc, B) = 100 · 𝔼c[ |φ(c≤B)| ]𝔼c[ ℓ(c≤B) ] (1)
Risk ρ(Dcx) = 𝔼[ u(c, x) ] / 𝔼[ |φ(c)| ]

Supported CBU per caption counts the claims the judge answers yes for; u(c, x) counts the claims it answers no for. Risk is the share of claimed CBUs a judge labels unsupported, so it aggregates captioner and judge errors.

Two judges, one question schema

The captioner Vc is Qwen3.5-35B-A3B-FP8. The extractor φ and the Qwen Judge share Qwen3.5-397B-A17B-FP8; the Gemma Judge, Gemma-4-31B-IT, comes from an independently trained family and re-asks the same extracted claims, so the judge family varies while the extractor stays fixed. Both answer with deterministic, schema-constrained decoding. Each CBU becomes one of three questions:

Is the visual claim '<TARGET>: <UNIT>' supported by the image?
Is the visual claim '<UNIT>' supported by the image?
Is the rendered text claim '<UNIT>' visibly supported by the image?

Key results

Every comparison fixes the source rows and varies only the captioning surface. Text statistics and prompt-pool support use paired rows per slice; the claim extractor and both judges read of those rows per surface ( on CC12M), and the two judges answer one question set.

Cross-corpus pairs

More supported claims and lower risk on every pair, under both judges

On each of the four cross-corpus pairs the released surface (Ours) raises supported CBU per caption and lowers unsupported risk under both the Qwen and the Gemma Judge. The supported-yield gain spans CBU per caption and the risk drop spans across the eight (pair, judge) cells.

Length is not the headline

Ours is longer than each reference except LAION-pop, where the two surfaces are length-matched ( vs. lex) and Ours still wins on yield, risk and pool-mass support.

Not carried by the hardest claim types

Without count and relation claims, the types VLM judges verify least reliably, Ours still raises supported CBU per caption by and lowers risk in all eight (pair, judge) cells.

Prompt pools

Per-pool prompt-mass deltas place Ours above the reference on of the seven prompt pools per pair; Figure 3 shows every pool.

CC12M case study

A long-vs-dense frontier, stable across two judges and four budgets

CC12M carries three released comparison surfaces with distinct policies. Among the long-form ones, PixelProse hard-codes openers and descriptive-narrator personas, and CC12M-LLaVA-NeXT carries no explicit opener hard-coding. At B = 64, Ours occupies the high-yield, low-risk corner; PixelProse reads as the highest-risk surface despite long captions (ρ = / under Qwen/Gemma at lex), and CC12M-LLaVA-NeXT sits between.

Length is not density

CC12M-Qwen3-VL† is the short-caption operating point: its -lex tag captions reach the highest CBU per 100 lex ( against for Ours) and the lowest risk (ρ = /) while stating claims per caption. Efficiency and yield therefore read jointly (Eq. 1): one 64-word window of Ours carries claims, a complete CC12M-Qwen3-VL† caption.

Budget sweep

Across B ∈ {16, 32, 48, 64} on all aligned images, claimed CBU per caption grows and CBU per 100 lex declines on every long-form surface, and Ours leads the long-form surfaces on both readings at every budget ( CBU per caption, per 100 lex).

Policy control

Same captioner, different policy: the gap follows the policy

Cross-corpus pairs compare surfaces written by different captioners, so the gain could be read as a property of the captioner family rather than of the policy π. The control holds Vc fixed and swaps only π: a naive surface from the same captioner on the same -image CC12M subset and a parallel DataComp subset, under a single user message that inherits the Recap-DataComp prompt body.

On both source families the naive policy under-yields the released one under each judge; measured risk drops alongside, the expected denominator effect on a lower-claim surface rather than a faithfulness gain. The naive surface is also longer than Ours yet mass-concentrated: frequent 5-token prefixes such as ( captions) and () escape the opener regex but are caught by top-100 prefix mass. After opener stripping, its content-prefix mass () exceeds every released CC12M surface on the same images (). Captioner family alone does not explain the cross-corpus gap.

Human study

Human ratings favor Ours on image support

annotators, blind to surface identity and machine labels, judged sampled CC12M claims first against the caption window and then against the image. The study holds primary judgments on claims; claims carry two independent labels, in each of the cells spanned by surface group and claim type.

The Qwen and Gemma Judges agree with humans at nearly identical rates. Human raters assign Ours the highest support rate of the four CC12M surfaces; none of its judgments is an explicit no, and uncertainty remains separate from support. Human explicit-no rates order the long-form surfaces as both judges' risk does: Ours (), LLaVA-NeXT (), PixelProse ().

Released captions

The release is a Hugging Face collection with one caption-only dataset per source family: nine families, five of them with the paired audits above and four released without paired audits.

Each dataset carries a Croissant 1.1 record. Source images and third-party reference captions are not redistributed; they are reached through their public releases and row-level join keys. The code repository carries the audit pipeline and the result summaries behind every table. Caption generation cost H200 GPU-hours.

Reproduce the profile

The audit is corpus-agnostic. A third party supplies caption text, source-row identifiers and, for the image-conditioned axis, paired image access; the released tokenizer, prompt pools, CBU schema, question template, label schema and manifest are reused as they are.

  1. Step 1

    Install and load captions

    The code uses uv and Python 3.11 or newer; uv.lock pins every dependency.

    git clone https://github.com/BootsofLagrangian/audit-recap-t2i.git
cd audit-recap-t2i
uv sync

    Captions stream from the Hugging Face collection, one dataset per family:

    from datasets import load_dataset

captions = load_dataset(
    "BootsofLagrangian/cc12m-recap-qwen3p5-35b-a3b",
    split="train", streaming=True)

  2. Step 2

    Text statistics and prompt pools

    Build the paired slices and the seven prompt pools, then run run_caption_fair_slice_surveys.py for the surface descriptors and caption_prompt_support_bootstrap.py for prompt-mass support and n-gram JSD.

    uv run python scripts/build_caption_fair_slices.py --all \
  --max-pairs 1000000 --seed 0
uv run python scripts/prepare_prompt_pools.py \
  --output-root data/prompt-pools/2026-04-24-expanded

  3. Step 3

    Claims and two judges

    Serve the extractor, build one request per caption window, and run it with run_text_json_requests.py; summarize_cbu_responses.py reports CBU/cap and CBU/100 lex. build_grounded_cbu_verify_requests.py attaches the images, build_cbu_vqa_requests.py and run_cbu_vqa_requests.py ask the questions, and summarize_cbu_vqa_responses.py reports supported CBU per caption and risk. The Gemma Judge answers the same request file with --model google/gemma-4-31B-it.

    bash scripts/vllm/serve_397b.sh start
uv run python scripts/build_caption_cbu_requests.py --input <surface>.jsonl \
  --output artifacts/cbu/<name>.requests.jsonl --surface <surface> --token-budget 64

    Full commands and flags: “Reproducing the paper” in the README
